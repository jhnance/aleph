# Decisions — 2026-06-07

## JWT sessions (not DB-backed sessions)

**Decision:** Sessions are signed JWTs (HS256) stored in `HttpOnly` cookies. No `sessions` table. JWT payload: `user_id`, `active_organization_id`, `exp` (30 days), `jti`. Org switching re-issues the JWT. Logout deletes the cookie client-side.

**Why:** DB-backed sessions require a round trip on every request; JWTs verify via signature only — pure CPU, no IO. `jti` is included now so future revocation support doesn't require a new token format; a `revoked_tokens` table can be added for exceptional cases later.

## Two Postgres roles for RLS bypass

**Decision:** Two roles — `aleph_app` (application, RLS enforced) and `aleph_service` (migrations/seeding, `BYPASSRLS`). The Fastify process connects as `aleph_app_user`; migrations connect as `aleph_service_user` via a separate connection string. These must never be swapped.

**Why:** Superuser connections are a security anti-pattern for application code. `BYPASSRLS` on a dedicated non-superuser role gives migrations the access they need without exposing full superuser privileges to the application.

## RLS policy shape

**Decision:** All tenant-scoped tables use `USING (organization_id = current_setting('app.current_org_id', true)::uuid)` with matching `WITH CHECK`. Tables with nullable `organization_id` (platform-provided data) use `organization_id IS NULL OR organization_id = ...` in `USING` but restrict writes to org-owned rows in `WITH CHECK`. `FORCE ROW LEVEL SECURITY` applied so even the table owner is subject to policies.

**Why:** `current_setting(..., true)` returns NULL rather than raising when the variable is unset, causing the policy to deny all access by default — the safe failure mode. The asymmetric read/write policy on platform-provided tables enforces that only Aleph (via the service role) can create platform rows.

## SDK/CLI: TypeScript-first, published to npm

**Decision:** The CLI is written in TypeScript and published to npm. Golden-path publish workflows are authored and hosted on the GitHub Actions marketplace. SDKs in other languages and build system plugins are post-MVP.

**Why:** TypeScript is the natural first SDK given the stack; npm distribution is the path of least resistance for that ecosystem.

---

## Search: self-hosted Meilisearch

**Decision:** Search and discovery is powered by self-hosted Meilisearch.

**Why:** Avoids a managed external service dependency while providing materially better search UX than Postgres full-text search (typo tolerance, relevance ranking, faceting). Self-hosting keeps data on-premise.

## Sibling-scoped slug uniqueness via partial indexes

**Decision:** Domain slug uniqueness is enforced per sibling group using two partial unique indexes:

```sql
CREATE UNIQUE INDEX idx_domain_slug_root  ON domains (organization_id, slug)            WHERE parent_id IS NULL;
CREATE UNIQUE INDEX idx_domain_slug_child ON domains (organization_id, parent_id, slug) WHERE parent_id IS NOT NULL;
```

This allows `Online/Pro` and `Offline/Pro` to coexist while preventing two `Pro` children under the same parent.

**Why not a single `UNIQUE (organization_id, parent_id, slug)` constraint?** SQL treats `NULL != NULL` in uniqueness checks — a single constraint with nullable `parent_id` would allow duplicate slugs among root domains (both have `parent_id = NULL`, considered distinct). The root partial index avoids this by excluding `parent_id` from its column list entirely.

**Why `CREATE UNIQUE INDEX` instead of `UNIQUE (...)`?** The `UNIQUE` constraint syntax doesn't support a `WHERE` clause. `CREATE UNIQUE INDEX` is the explicit form that enables partial indexes; both create the same underlying structure.

## Active org on magic link sign-in

**Decision:** At sign-in, if the user has exactly one org membership, that org is set as the `org` claim in the JWT. If zero or multiple memberships exist, `org` = null and the user selects via org-switching.

**Why:** Always returning null forces single-org users to explicitly select their only org — unnecessary friction. "Exactly one" is the only case where auto-selection is unambiguous; multiple-org users must still choose explicitly.

*Revised from: `org` = null always.*

## Create Organization: optional auto-switch

**Decision:** `POST /organizations` accepts an optional `switchToOrg: boolean` flag (default: false). If true, the server re-issues the JWT with `org` set to the new org id and replaces the cookie in the same response.

**Why:** Auto-switching is the likely desired behavior when creating a new org, but shouldn't be imposed — a user creating an org on behalf of a team may not want to immediately leave their current session context.
