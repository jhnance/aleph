# Decisions — 2026-06-07

## JWT sessions (not DB-backed sessions)

**Decision:** Sessions are signed JWTs (HS256) stored in `HttpOnly` cookies. No `sessions` table. JWT payload: `user_id`, `active_organization_id`, `exp` (30 days), `jti`. Org switching re-issues the JWT with the updated `active_organization_id`. Logout deletes the cookie client-side.

**Why:** DB-backed sessions require a round trip on every request to validate the session token. JWTs verify via signature only — pure CPU, no IO. Simplicity and reduced DB load were the priority. Revocability is not a major concern; a `revoked_tokens` table can be added later for exceptional cases (security incidents, admin-forced logout). `jti` is included in the payload now so that future revocation support doesn't require a new token format.

## Two Postgres roles for RLS bypass

**Decision:** Two roles — `aleph_app` (application, RLS enforced) and `aleph_service` (migrations/seeding, `BYPASSRLS`). The Fastify process connects as `aleph_app_user`. Migrations connect as `aleph_service_user` via a separate connection string. These must never be swapped.

**Why:** Superuser connections are a security anti-pattern for application code. `BYPASSRLS` on a dedicated non-superuser role gives migrations the access they need without exposing full superuser privileges to the application process or to migration scripts.

## RLS policy shape

**Decision:** All tenant-scoped tables use `USING (organization_id = current_setting('app.current_org_id', true)::uuid)` with `WITH CHECK` matching. Tables with nullable `organization_id` (platform-provided data) use `organization_id IS NULL OR organization_id = ...` in `USING` but restrict writes to org-owned rows only in `WITH CHECK`. `FORCE ROW LEVEL SECURITY` is applied so even the table owner is subject to policies.

**Why:** `current_setting(..., true)` returns NULL rather than raising an error when the variable is unset — causing the policy to deny all access by default, which is the safe failure mode. The asymmetric read/write policy on platform-provided tables enforces that only Aleph (via the service role) can create platform rows.

## Sibling-scoped slug uniqueness via partial indexes

**Decision:** Domain slug uniqueness is enforced per sibling group (not org-wide) using two partial unique indexes:

```sql
CREATE UNIQUE INDEX idx_domain_slug_root  ON domains (organization_id, slug)            WHERE parent_id IS NULL;
CREATE UNIQUE INDEX idx_domain_slug_child ON domains (organization_id, parent_id, slug) WHERE parent_id IS NOT NULL;
```

This allows `Online/Pro` and `Offline/Pro` to coexist, while still preventing two `Pro` children under the same parent.

**Why not a single `UNIQUE (organization_id, parent_id, slug)` constraint?** SQL treats `NULL != NULL` in uniqueness checks. A single constraint including nullable `parent_id` would allow duplicate slugs among root domains (both have `parent_id = NULL`, which are considered distinct). The root partial index avoids this by excluding `parent_id` from its column list entirely — it only covers root rows and enforces uniqueness on `(organization_id, slug)` among them.

**Why `CREATE UNIQUE INDEX` instead of `UNIQUE (...)`?** The `UNIQUE` constraint syntax inside `CREATE TABLE` doesn't support a `WHERE` clause. `CREATE UNIQUE INDEX` is the explicit form that enables partial indexes. Both create the same underlying structure — PostgreSQL implements unique constraints as unique indexes internally.
