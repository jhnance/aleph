## SSR for all routes with React Router v7

**Context:** Deciding the rendering strategy for `apps/web`. The web app was bare-bones CSR (Vite + React). Two questions: which pages get SSR, and which framework.

**Decision:** All routes are SSR using React Router v7 (framework mode). The web app becomes a separate Node server. Loaders call the Fastify API over HTTP — no direct DB access from the web layer.

**Rationale:** Multitenant apps have a higher blast radius when tenant isolation leaks. SSR eliminates the flash-of-unauthorized-content window entirely — auth checks in loaders redirect before HTML is sent. It also enables HttpOnly cookies as the sole auth credential storage, removing session tokens from JS-accessible storage (mitigates XSS token theft per OWASP guidance). React Router v7 is the most mature Vite-native SSR option and its loader model maps cleanly onto per-route data fetching.

## clientLoader as client-side navigation layer

**Context:** During SSR setup alignment, the question arose whether to do "org-shell SSR + SPA interior" for fast in-app navigation.

**Decision:** Full SSR for all routes. Use React Router v7's `clientLoader` per-route (as an optimization, not at setup time) for fast in-app navigations without sacrificing the SSR security contract.

**Rationale:** Org-shell + SPA interior reintroduces flash on deep links, breaks per-URL ETags (required by ssr-page-freshness), and puts client-side code in the tenant isolation chain. `clientLoader` provides the same navigation speed benefit: the server `loader` runs on direct/fresh visits (SSR, auth-checked), and `clientLoader` handles subsequent in-app navigations from a client cache. No tradeoff required.

## ETag source for SSR page freshness

**Context:** The `ssr-page-freshness` stub listed two ETag candidates: content-ID hash vs. rendered-HTML hash.

**Decision:** Hash of primary content IDs (head `use_cases.id` for view-use-case; representative version ID + sorted attachment IDs for point-detail).

**Rationale:** Hashing the rendered HTML requires a full render before knowing whether to 304, defeating the efficiency gain. Content IDs are available from a single lightweight query, stable per published record, and sufficient to detect any change that would affect rendered output.
