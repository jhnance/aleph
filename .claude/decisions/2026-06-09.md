# Decisions — 2026-06-09

## Use case authoring: `.aleph.ts` files with `defineUseCase()`

Each use case demo and its mocks are defined in a `.aleph.ts` file co-located with source code. The written description (title, content) lives in Aleph. The `.aleph.ts` file owns the demo entry point, MSW handlers, and the stable use case identity. The complete field set:

```typescript
export default defineUseCase({
  id: 'login-flow',            // stable identifier — treat as immutable
  title: 'Login Flow',         // display name — editable via `aleph sync` or Aleph UI
  export: 'LoginButton',       // optional — scopes use case to a named export
  demo: './LoginFlowDemo.tsx', // path to demo entry point
  handlers: [                  // MSW mock handlers
    http.post('/api/auth/login', () =>
      HttpResponse.json({ token: 'mock-token-123' })
    )
  ]
})
```

**Why:** Co-location keeps demo artifacts in version control alongside the code they demonstrate. Separating `id` (immutable) from `title` (mutable) decouples stable identity from display name, avoiding the Storybook problem where title-based identity breaks on renames.

## Use case identity: explicit `id` in `.aleph.ts` (Option C)

Each `.aleph.ts` file carries a stable `id` that is the lineage key in Aleph. The CLI uses this ID directly — no heuristics, no central registry. The ID travels with the file on moves and renames.

**Why:** Heuristic matching (lock file path + title similarity) fails silently when both change simultaneously and is problematic in CI. A central config registry requires manual two-step maintenance. Explicit ID is unambiguous and the Storybook lesson is clear: optional IDs are ignored by most users; the mechanism must be automatic or enforced.

---

## Two use case creation flows

1. **CLI-first:** `aleph new use-case [--title="..."] [--export="..."]` — CLI generates a UUID-based `id`, creates a pending record in Aleph via the API, scaffolds a `.aleph.ts` file pre-populated with the generated ID.
2. **Aleph-UI-first:** user creates the use case in Aleph's UI (getting an ID), copies the ID, runs `aleph new use-case --id=<id>` — CLI verifies the ID exists in Aleph, scaffolds the `.aleph.ts` file only (no new Aleph record created).

In both flows, the `.aleph.ts` file is the output. `aleph scan` is run separately afterward to update the lock file.

**Why:** Both engineer-initiated and non-engineer-initiated creation must be supported. A single `aleph new use-case` entry point handles both, with `--id` as the flag that distinguishes them.

---

## Lock file format (`aleph.lock`)

A JSON file at the project root tracking the canonical set of use case IDs declared by the point. IDs are grouped by export name (export-scoped) or under `"point"` (point-level):

```json
{
  "useCases": {
    "exports": {
      "Button": ["login-flow", "logout"]
    },
    "point": ["module-initializes-without-side-effects"]
  }
}
```

No file paths are stored — only IDs. Files can move freely as long as the `id` in each `.aleph.ts` file is unchanged.

**Why:** The lock file guards against unintended use case removals at publish time. Excluding paths keeps the file stable across refactors and makes the diff signal-to-noise ratio high (only ID-level changes matter).

---

## `aleph scan` command

Recursively finds all `.aleph.ts` files, extracts IDs grouped by their `export` field (or `"point"` if absent), diffs against the current lock file, prompts the user to confirm additions and removals, then writes the updated lock file. Intended to be run before committing and before `aleph publish`.

**Why:** Separates the interactive lock file confirmation step from the publish step, keeping CI clean. `aleph publish` reads the committed lock file without prompting.

---

## `aleph sync` command

Bidirectional title reconciliation between local `.aleph.ts` files and Aleph. Pulls title edits from the Aleph API down to local files; detects local title edits and pushes them up via the draft → publish flow. On conflict (both local and remote changed since last sync), prompts the user to choose: keep local, keep remote, or edit manually.

**Why:** Keeps `aleph publish` focused on versioning. Title sync is a discrete interactive operation that produces a committed local state, which publish can then read cleanly.

---

## `aleph publish` preflight checks

`aleph publish` runs `aleph scan` and `aleph sync` silently as a preflight. If either surfaces diffs, publish stops and instructs the user to run the relevant command first. If both pass cleanly, publish proceeds.

**Why:** Prevents silent divergence between the lock file / Aleph titles and the codebase (the problem with a sync-only approach), without making publish itself a multi-purpose interactive command (the problem with publish-does-everything). Follows the `git push` model: fail fast, give the user explicit control.

---

## Demo artifacts: `demo_artifact_url` on `point_version_use_cases`

A nullable `demo_artifact_url TEXT` column is added to `point_version_use_cases`. It is populated at publish time when the CLI builds and uploads a demo artifact for the (version, use case) pair. It is null for UI-authored use cases that have no `.aleph.ts` file. Forward propagation does NOT copy `demo_artifact_url` — each version's demo must be explicitly published.

**Why:** A demo artifact is a build artifact tied to a specific version of the code; copying it forward would incorrectly imply the new version's behavior is identical. A null `demo_artifact_url` affects the point's health score.

---

## `--release-type` flag replaces `--is-prerelease` / `--is-hotfix`

`aleph publish` accepts `--release-type=release|prerelease|hotfix|metadata`. The CLI infers it where unambiguous (no suffix → `release`, `+` suffix → `metadata`) and requires it for `-` suffix versions. Deferred alternative: a committed "release intent" document (changeset-style) that `aleph publish` reads instead of a flag — cleaner for monorepo workflows but adds a pre-publish authoring step. Not adopted now; revisit if the flag UX proves awkward in practice.

## Open question: `aleph new use-case` CLI-first — pre-publish Aleph record shape

When `aleph new use-case` (no `--id`) creates a record in Aleph before first publish, what does it create? Options: (a) a `draft_use_cases` row with a pre-generated `future_lineage_id` field (shown as "use case ID" in the UI for the Aleph-UI-first flow), or (b) a `use_case_lineages` row with a `status = 'pending'` field, or (c) no Aleph record at all — lineage created at first `aleph publish` using the pre-generated UUID. Must be resolved before implementing `aleph new use-case`.
