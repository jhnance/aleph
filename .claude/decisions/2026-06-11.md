# Decisions — 2026-06-11

## Per-command RLS policies on nullable-org tables

**Decision:** Split the single `FOR ALL` policy on nullable-org tables (`frontend_frameworks`, `custom_point_types`) into four per-command policies: `FOR SELECT` allows platform + own rows; `FOR INSERT`/`FOR UPDATE`/`FOR DELETE` restrict to own-org rows in both `USING` and `WITH CHECK`. Platform rows are writable only via `aleph_service` (`BYPASSRLS`).

**Why:** `USING` governs which rows UPDATE and DELETE may target, and DELETE never consults `WITH CHECK` — so the broad `FOR ALL` `USING` clause let any tenant delete a platform row or UPDATE it into their own org. Per-command policies exactly match the intended invariant with no schema change.

## Access-matrix convention for security mechanisms

**Decision:** Every security mechanism (RLS policy, role grant, auth check) is designed with an explicit access matrix — command × actor/row class — with every cell filled from documented semantics before the design lands in a doc. First application: the nullable-org policy matrix in `design/data-model.md`.

**Why:** The `FOR ALL` hole survived the original design session and was caught only by an adversarial review pass. The convention forces that mode mechanically, the same way worked concurrency examples catch race bugs.

---

## Identity-plane RLS: hybrid posture

**Decision:** Hybrid, decided by what session context exists when each table is touched. `auth_codes` + `users`: RLS-exempt with documented app guards (all access confined to the auth module; hash-keyed atomic UPDATE, email upsert, JWT-sub reads). `organizations` + `organization_memberships`: user-keyed policies on a new `app.current_user_id` session variable, set by the preHandler alongside the org id. Org INSERT requires only an authenticated user; role checks stay app-layer. The login transaction sets `app.current_user_id` manually after the user upsert. Invite flow must re-check the memberships INSERT branches when designed.

**Why:** User-keyed policies go exactly where every access is authenticated and leakage is cross-tenant (membership facts). The exempt tables are unkeyable by session context — magic-link flows run unauthenticated — and leak only identity metadata if the app layer fails, not catalog data.

## Session cookie: SameSite=Lax + CSRF posture

**Decision:** `HttpOnly; Secure; SameSite=Lax; Path=/`. Defense-in-depth on mutating routes: `Origin` header verification when present + `Content-Type: application/json` required. Accepted residual risk: login CSRF via an attacker's own magic link — negligible payoff for a catalog tool.

**Why:** `Lax` closes the entire cross-site POST/fetch attack surface. `Strict` adds protection only for mutating top-level GETs (none under cookie authority here) and would break shared deep links — signed-in users arriving from Slack would land on a login page, and shared deep links are the product.

## Transactions scoped to DB work + server-enforced timeouts

**Decision:** A `withRequestContext` helper opens a transaction, sets both RLS vars as its first statement, runs only DB statements, then commits. External effects: inputs before the transaction (S3 upload-before-POST already complies), outputs after commit (email, Meilisearch). Long-running work is async. Role-level timeouts on `aleph_app`: statement 5s, lock 2s, idle-in-transaction 10s, transaction 30s (Postgres ≥ 17 required for `transaction_timeout`); `aleph_service` exempt; publish raises its budget to 15s via `SET LOCAL`.

**Why:** External IO inside a transaction converts a provider brownout into pool exhaustion and lock convoys. The previous approach (request-spanning transaction as the RLS context carrier) welded transaction lifetime to request lifetime, external IO included. Timeouts make the scoping convention self-enforcing against future violations.

---

## URL org authoritative; JWT slimmed to identity; membership checked per request

**Decision:** The URL org is authoritative. JWT claims: `sub`, `exp`, `iat`, `jti` only. Org-scoped routes run one indexed query inside the request transaction (org by slug ⋈ membership by user), yielding org id + role; no row → 404 (tenant-hiding). Sequencing: `set_config(user)` → membership query → `set_config(org)`. Org switching becomes pure navigation — the switch endpoint and `org_context_mismatch` error are deleted. The membership check is never cached.

**Why:** One indexed query (PK + unique-index reads on an already-open transaction) closes the revocation gap to zero, makes role changes per-request fresh, fixes multi-tab and deep links structurally, and deletes an auth flow. The previous JWT-carries-org approach silently mixed cross-tenant data in multi-tab scenarios and left a 30-day revocation window.

**Residual:** user-level revocation via `jti`-keyed denylist; JWT-secret rotation as backstop.
