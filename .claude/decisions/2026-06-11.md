# Decisions — 2026-06-11

## Per-command RLS policies on nullable-org tables

**Context:** Phase 3 security session, item 3.1. The single `FOR ALL` policy on nullable-org tables (`frontend_frameworks`, `custom_point_types`) used a broad `USING` (platform + own rows) with a narrow `WITH CHECK`. `USING` governs which existing rows UPDATE and DELETE may target, and DELETE never consults `WITH CHECK` — so any tenant could delete a platform row or UPDATE it into its own org (hijack).

**Decision:** Split into four per-command policies: `FOR SELECT` allows platform + own rows; `FOR INSERT`/`FOR UPDATE`/`FOR DELETE` restrict to own-org rows in both `USING` and `WITH CHECK`. Platform rows are writable only via `aleph_service` (`BYPASSRLS`).

**Rationale:** Exactly matches the intended invariant ("tenants read platform rows, never modify them") with no schema change. Rejected alternative: splitting platform and tenant rows into separate tables — cleaner ownership, but it forks every referencing FK (`frontend_components.framework`, `custom_points.custom_type_id`) into dual nullable columns + CHECK, a recurring tax for protection the policies provide for free.

## Access-matrix convention for security mechanisms

**Context:** The `FOR ALL` hole survived the original design session and was caught only by the adversarial review pass. Diagnosis: design mode verifies artifacts against *intent* ("USING = reads, WITH CHECK = writes") rather than against the mechanism's *documented semantics* (per-command clause evaluation).

**Decision:** Convention added to ALIGNMENT.md: every security mechanism (RLS policy, role grant, auth check) is designed with an explicit access matrix — command × actor/row class — with every cell filled from documented semantics before the design lands in a doc. First application: the nullable-org policy matrix in `design/data-model.md`.

**Rationale:** Forces the adversarial mode into the design session mechanically, the same way worked concurrency examples (Alice/Bob) catch race bugs. Review remains the backstop; the convention lowers the miss rate for the known semantics-vs-intent gap class.

## Identity-plane RLS: hybrid posture

**Context:** Phase 3 security session, item 3.2(a). `auth_codes`, `users`, `organizations`, and `organization_memberships` predate or sit outside any single org context, so the org-keyed policy can't cover them. The review framed it as exempt-with-documented-app-guards *or* user-keyed policies; the per-table analysis showed pure user-keying was never possible — the magic-link flows run unauthenticated, with no session context to key on.

**Decision:** Hybrid, decided by what session context exists when each table is touched. `auth_codes` + `users`: RLS-exempt with documented app guards (all access confined to the auth module; hash-keyed atomic UPDATE, email upsert, JWT-sub reads). `organizations` + `organization_memberships`: user-keyed policies on a new `app.current_user_id` session variable, set by the preHandler alongside the org id. Org INSERT requires only an authenticated user (the owner membership row FK-references the org row, so a membership-keyed WITH CHECK is structurally impossible at insert time); role checks (owner/admin) stay app-layer. The login transaction sets `app.current_user_id` manually after the user upsert. Invite flow (checklist 4.1) must re-check the memberships INSERT branches when designed.

**Rationale:** User-keyed policies go exactly where (a) every access is authenticated and (b) leakage is genuinely cross-tenant (membership facts). The exempt tables are unkeyable, small-surface, single-module, and leak only identity metadata if the app layer fails — not catalog data.

## Session cookie: SameSite=Lax + CSRF posture

**Context:** Phase 3 security session, item 3.2(b)–(c). Cookie-borne sessions had no SameSite/CSRF decision.

**Decision:** `HttpOnly; Secure; SameSite=Lax; Path=/`. Load-bearing criterion: no GET endpoint mutates state under the cookie's authority (`/api/auth/verify` mutates but is credentialed by the emailed token, not the cookie). Defense-in-depth on mutating routes: `Origin` header verification when present + `Content-Type: application/json` required. Accepted residual risk, documented: login CSRF via an attacker's own magic link — negligible payoff for a catalog tool; mitigating it fights the magic-link UX.

**Rationale:** `Lax` closes the entire cross-site POST/fetch attack surface. `Strict` adds protection only for mutating top-level GETs (we have none under cookie authority) and would break shared deep links — signed-in users arriving from Slack would land on a login page, and shared deep links are the product.
