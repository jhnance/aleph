# Decisions — 2026-06-10

Decisions adopted while triaging the 2026-06-09 multi-agent design review.

## Titles are Aleph-authoritative; `aleph sync` is pull-only; publish warns on drift

**Decision:** The Aleph record is the single source of truth for use case titles. `aleph sync` overwrites local titles from Aleph with a summary of changes; local title edits are never pushed. `aleph publish` emits a non-fatal warning when a local title differs from Aleph, suggesting `aleph sync`.

**Why:** Pull-only with one authority is the simplest coherent model. It eliminates the "which version does a title push publish against" question entirely — titles live on content records and pushing from the CLI would force a publish, which is the wrong tool for a rename.

**Supersedes:** bidirectional sync and the sync preflight in `decisions/2026-06-09.md`.

---

## Use case IDs are UUIDs — no slugs

**Decision:** The `id` in `.aleph.ts` files, the lock file, and the Aleph API is always a UUID. No slug column on `use_case_lineages`; the UUID in the file *is* (or becomes) the lineage ID. The `title` is the human-readable handle.

**Why:** The slug had no home in the data model (examples used slugs while the schema PK and CLI-first flow both used UUIDs). Adding a slug column buys nothing — title already carries the human meaning.

---

## Authorization baseline: viewer reads, member writes, admin manages org resources

**Decision:** Role gates, enforced at the application layer:
- `viewer` — read-only across the entire API.
- `member`+ — catalog writes: domains, points, point statuses, versions (publish), drafts, use cases, connections.
- `admin`+ — org-level resource management: custom point types, org-defined frameworks, invites (future), org settings (future).
- `owner` — reserved for org lifecycle (transfer/delete org; future).

Insufficient role returns **403**.

**Why:** Roles were decided on 2026-06-06 but no use case applied them — as specced, a `viewer` could create and delete everything. Each mutating use case now carries a one-line role requirement.

---

## Status code conventions

Not-found-or-other-org returns **404** (tenant-hiding); **403** is reserved for authorization denials (insufficient role, org-context mismatch, non-membership on org switch).

---

## Org-scoped API routes carry the org slug: `/api/orgs/:orgSlug/...`

**Decision:** All org-scoped resources are addressed under `/api/orgs/:orgSlug/` (e.g. `POST /api/orgs/acme/domains`). Auth routes and org creation remain global. The `:orgSlug` must match the active org in the session JWT; a mismatch returns **403** with `org_context_mismatch`. SPA routes mirror the API.

**Why:** With the active org only in a shared cookie, an org switch in one tab silently re-scoped every other tab's requests while their rendered state belonged to the old org. Org-in-path makes every request self-describing and turns the multi-tab case into a loud 403.

**Open (security session):** whether the URL org should become *authoritative* (per-request membership check) or remain a consistency check against the JWT. Resolved in `decisions/2026-06-11.md`.

---

## Object storage: AWS S3

**Decision:** Demo artifacts are stored in S3. Artifacts are uploaded before `POST .../versions` via pre-signed URLs, so `point_version_use_cases` rows are written once and complete — keeping the table's immutability intact.

---

## No server-side forward propagation; the publish payload is the use case set

**Decision:** A version's use case attachments are exactly what the `POST .../versions` payload declares (`useCases: [{ lineageId, title, exportName?, demoArtifactUrl }]`). The server never copies attachments from the predecessor. Omission from the payload means the use case doesn't appear on the new version.

**Why:** Server-side copying was an anachronism predating `.aleph.ts`/`aleph.lock`. Once those became the source of truth, the copy was a second writer fighting the payload and the sole source of the trigger-collision and NULL-demo problems.

**Supersedes:** forward-propagation criterion in `publish-point-version.md` and propagation language in the 06-09 demo-artifact decision.

---

## Export scoping lives on the attachment, not the lineage

**Decision:** `use_case_lineages` carries no `export_id`; scoping moved to `point_version_use_cases.export_id` (NULL = point-level in that version). Manifest presence enforced by a compound FK to `point_version_exports`. `lineage_id` is denormalized onto attachment rows with `UNIQUE (point_version_id, lineage_id)`.

**Why:** Scoping is a fact about a (version, use case) pair — one lineage can attach to `CarouselItem` in v1.0.0 and `CarouselSlide` in v2.0.0. Keeping the `.aleph.ts` UUID as the lineage ID across export renames requires the lineage itself to survive them.

---

## Every attachment has a demo; the UI is a drafting surface

**Decision:** `demo_artifact_url` is NOT NULL. Demos are immutable and attached at release time; they never carry between versions. The UI authors and edits language only — it never creates version attachments. A `metadata`-classified release is the vehicle for doc-only additions.

**Why:** A demo artifact is a build artifact tied to specific version code; copying it forward would imply identical behavior.

---

## Unpublish, never delete

**Decision:** Retracting a use case claim sets `unpublished_at` on that one attachment row — hidden from default read paths, retained, visible to org `admin`+, republishable. No hard deletion; no cascade. Attachment rows are mutable in exactly two columns: `use_case_id` (forward re-point on content edit) and `unpublished_at`.

**Why:** Free editing of published claims would erode catalog trustworthiness, but inflexibility is its own failure. The published fact is permanent; its visibility as a current claim is not.

---

## `aleph.config.ts` is for discovery; use cases are files-only

**Decision:** The root config carries `pointId`, `apiBaseUrl`, `org`, export-detection entries, use case discovery globs, and (future) dependency declarations. Use cases are declared exclusively in co-located `.aleph.ts` files — never inline in config.

Also resolved: a pre-publish use case is a `use_case_lineages` row plus a mutable draft. The lineage is registered at draft creation; brand-new use cases have no UI publish step — the CLI version publish that attaches the use case promotes the draft to the first content record. `draft_use_cases.lineage_id` is NOT NULL.
