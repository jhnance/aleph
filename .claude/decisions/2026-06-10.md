# Decisions — 2026-06-10

Decisions adopted while triaging the 2026-06-09 multi-agent design review (see `.claude/review-checklist.md` for the full worklist and annotation context).

## Titles are Aleph-authoritative; `aleph sync` is pull-only; publish warns on drift

**Decision:** The Aleph record is the single source of truth for use case titles. `aleph sync` pulls remote titles into local `.aleph.ts` files (overwriting local edits, with a summary of what changed). Local title edits are never pushed — not by `aleph sync`, not by `aleph publish`. `aleph publish` emits a non-fatal warning when a local title differs from Aleph, suggesting `aleph sync`.

**Why:** The 2026-06-09 log contained an unresolved in-file reversal (bidirectional sync → pull-only) and three artifacts told three different title stories, leaving local title edits with no specified path. Pull-only with one authority is the simplest coherent model; it eliminates the "which version does a title push publish against" question entirely (titles live on content records — pushing from the CLI would force a publish, which is the wrong tool for a rename). The 06-09 conflict-resolution prompt (keep local / keep remote) is moot under this model and is removed.

**Supersedes:** the "Bidirectional title reconciliation" section and the "scan **and sync**" preflight in `decisions/2026-06-09.md` (amended in place).

## Use case IDs are UUIDs — no slugs

**Decision:** The `id` in `.aleph.ts` files, the lock file, and the Aleph API is always a UUID. There is no slug or external-identifier column on `use_case_lineages`; the UUID in the file *is* (or becomes) the lineage ID. The `title` is the human-readable handle.

**Why:** The 06-09 examples used slugs (`'login-flow'`) while the schema PK and the CLI-first flow both used UUIDs — the slug had no home in the data model. Adding a slug column buys readability inside a generated file nobody hand-addresses, at the cost of a uniqueness scope and a second identity. Title already carries the human meaning.

## Authorization baseline: viewer reads, member writes, admin manages org resources

**Decision:** Role gates, enforced at the application layer:
- `viewer` — read-only across the entire API.
- `member`+ — catalog writes: domains, points, point statuses, versions (publish), drafts, use cases, connections.
- `admin`+ — org-level resource management: custom point types, org-defined frameworks, invites (future), org settings (future).
- `owner` — reserved for org lifecycle (transfer/delete org; future).

Insufficient role returns **403**.

**Why:** Roles were decided on 2026-06-06 but no use case applied them — as specced, a `viewer` could create and delete everything, and retrofitting checks post-launch is an API behavior change. Each mutating use case now carries a one-line role requirement.

## Status code conventions

Not-found-or-other-org returns **404** (tenant-hiding); **403** is reserved for authorization denials (insufficient role, org-context mismatch, non-membership on org switch).

## Org-scoped API routes carry the org slug: `/api/orgs/:orgSlug/...`

**Decision:** All org-scoped resources are addressed under `/api/orgs/:orgSlug/` (e.g. `POST /api/orgs/acme/domains`). Auth routes (`/api/auth/*`) and org creation (`POST /api/orgs`) remain global. The `:orgSlug` must match the active org in the session JWT; a mismatch returns **403** with error code `org_context_mismatch`. The SPA resolves a mismatch (e.g. a deep link into another org the user belongs to) by calling the org-switch endpoint and retrying. SPA routes mirror the API: the org slug is in the URL path.

**Why:** With the active org living only in a shared cookie, an org switch in one tab silently re-scoped every other tab's requests while their rendered state belonged to the old org — cross-tenant data mixing in the UI. Org-in-path makes every request and every deep link self-describing, and turns the multi-tab case into a loud 403 instead of silent mixing.

**Open (security session):** whether the URL org should become *authoritative* (requiring a per-request membership check, which conflicts with the no-DB-lookup JWT model) or remain a consistency check against the JWT as decided here. This pairs with the 30-day membership-revocation question.

## Object storage: AWS S3

**Decision:** Demo artifacts are stored in S3. Added to the architectural constraints in ALIGNMENT.md. Artifacts are uploaded *before* `POST .../versions` (pre-signed URLs), so `point_version_use_cases` rows are written once and complete — keeping the table's immutability trigger intact. Exact payload mechanics to be settled in the publish-knot session.
