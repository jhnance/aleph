# Decisions — 2026-06-06

## `frontend_frameworks` as a table, not an enum

**Decision:** Keep `frontend_frameworks` as a table with a nullable `organization_id` (`NULL` = platform-provided, non-null = org-defined), rather than a Postgres enum.

**Why:** Organizations may want to define their own custom frameworks. A table supports this; an enum does not without a schema migration. The nullable org pattern allows Aleph to seed well-known frameworks globally while letting each org extend the list.

---

## `custom_point_types` for org-defined point types

**Decision:** Add a `custom_point_types` table (same nullable `organization_id` pattern) and a `custom_points` extension table, with `'custom'` added to the `point_type` enum as a discriminator.

**Why:** Platform-defined types (like `frontend_component`) have bespoke extension tables with structured metadata. Org-defined types are labels only — no structured metadata. Slotting `'custom'` into the existing discriminator pattern keeps the architecture consistent while giving orgs flexibility.

---

## Roll-your-own auth with magic links

**Decision:** Build custom magic link / OTP authentication rather than delegating to a third-party provider (Clerk, Auth0, etc.).

**Why:** Full control, no vendor dependency, and the implementation is well-understood. The `users` and `auth_codes` tables cover the magic link flow. Sessions are JWT-based — no sessions table. Single-use enforcement for auth codes is atomic via `UPDATE ... WHERE used_at IS NULL ... RETURNING id`.

---

## SHA-256 for token hashing (not bcrypt)

**Decision:** Hash magic link tokens and session tokens with SHA-256.

**Why:** Tokens are 32 cryptographically random bytes (2²⁵⁶ possible values). Security comes from token entropy, not hash slowness — bcrypt's deliberate slowness is only valuable against low-entropy inputs like passwords. SHA-256 via Node's `crypto.createHash('sha256')` is correct here. [Kerckhoffs's principle](https://en.wikipedia.org/wiki/Kerckhoffs%27s_principle) (originally stated in Auguste Kerckhoffs' 1883 "La Cryptographie Militaire"): a system should be secure even if everything except the secret itself is public knowledge. The algorithm being known is irrelevant; the entropy of the token is what provides security.

---

## Atomic single-use enforcement for auth codes

**Decision:** Redeem auth codes with a single `UPDATE ... WHERE used_at IS NULL AND expires_at > now() RETURNING id` inside a transaction, not a separate SELECT then UPDATE.

**Why:** A 2024 incident demonstrated that checking and stamping `used_at` in separate statements allows two concurrent requests (200ms apart) to both pass the check before either stamps it. The atomic UPDATE collapses existence, validity, and consumption into one operation.

---

## `sql.reserve()` + `SET LOCAL` for RLS connection context

**Decision:** Use `sql.reserve()` to hold a dedicated postgres.js connection per request, manually `BEGIN`, `SET LOCAL app.current_user_id`, `COMMIT`/`ROLLBACK` in Fastify lifecycle hooks.

**Why:** `SET LOCAL` scopes the variable to the current transaction — context resets automatically when the transaction ends, preventing leakage across pooled connections. `sql.begin()` was rejected because it takes a callback wrapping the whole transaction body, making it incompatible with Fastify's multi-hook request lifecycle. `sql.reserve()` is the correct primitive for spanning a connection across hooks.

---

## Multiple organizations per user

**Decision:** Users can be members of multiple organizations. `organization_memberships` is a join table with a composite PK on `(user_id, organization_id)`.

**Why:** Initially considered single-org per user (simpler RLS, `organization_id` on `users`), but a user might want conceptual separation between multiple different ecosystems within Aleph. Multi-org is the right default.

---

## Organization membership roles: `owner`, `admin`, `member`, `viewer`

**Decision:** Four roles as a Postgres enum on `organization_memberships`.

**Why:** Covers the range from full control (`owner`) to read-only access (`viewer`). Roles are application-layer authorization — RLS only checks membership presence, not role.

---

## RLS isolation boundary: org-level (not domain-level)

**Decision:** RLS policies enforce org-level isolation for now. Domain-level access control is a future concern.

**Why:** Domain membership (assigning users to specific domains) is in scope eventually but not for this phase. Org-level isolation is sufficient for MVP and simpler to implement correctly.

---

## Connections, sub-domains, SDK/CLI, email, and search are MVP scope

**Decision:** All of the following are in scope for MVP: Connections between Points, sub-domain hierarchy, SDK/CLI publish workflow, email sending for magic links, search and discovery.

**Why:** These are either core to the value proposition (Connections, search) or prerequisite infrastructure (email, SDK/CLI). None can be deferred without significantly compromising the product.

---

## Admin reporting dashboard is post-MVP

**Decision:** A special admin view with ecosystem-wide insights (across domains and sub-domains) is explicitly deferred.

**Why:** All roles see the same UI for MVP. The admin dashboard is a nice-to-have that doesn't block core cataloguing and discovery functionality.
