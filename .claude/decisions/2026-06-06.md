# Decisions — 2026-06-06

## `frontend_frameworks` as a table, not an enum

**Decision:** Keep `frontend_frameworks` as a table with a nullable `organization_id` (`NULL` = platform-provided, non-null = org-defined), rather than a Postgres enum.

**Why:** Organizations may define their own custom frameworks; a table supports this, an enum doesn't without a schema migration. The nullable org pattern lets Aleph seed well-known frameworks globally while allowing each org to extend the list.

---

## `custom_point_types` for org-defined point types

**Decision:** Add a `custom_point_types` table (same nullable `organization_id` pattern) and a `custom_points` extension table, with `'custom'` added to the `point_type` enum as a discriminator.

**Why:** Platform-defined types have bespoke extension tables with structured metadata; org-defined types are labels only. Slotting `'custom'` into the existing discriminator pattern keeps the architecture consistent while giving orgs flexibility.

---

## Roll-your-own auth with magic links

**Decision:** Build custom magic link / OTP authentication rather than delegating to a third-party provider (Clerk, Auth0, etc.). Sessions are JWT-based — no sessions table. Single-use enforcement for auth codes is atomic via `UPDATE ... WHERE used_at IS NULL ... RETURNING id`.

**Why:** Full control, no vendor dependency, and the implementation is well-understood.

---

## SHA-256 for token hashing (not bcrypt)

**Decision:** Hash magic link tokens and session tokens with SHA-256.

**Why:** Tokens are 32 cryptographically random bytes — security comes from token entropy, not hash slowness. bcrypt's deliberate slowness defends against low-entropy inputs like passwords and adds nothing here.

---

## Atomic single-use enforcement for auth codes

**Decision:** Redeem auth codes with a single `UPDATE ... WHERE used_at IS NULL AND expires_at > now() RETURNING id` inside a transaction, not a separate SELECT then UPDATE.

**Why:** A separate SELECT then UPDATE allows two concurrent requests to both pass the check before either stamps `used_at`. The atomic UPDATE collapses existence, validity, and consumption into one operation.

---

## `sql.reserve()` + `SET LOCAL` for RLS connection context

**Decision:** Use `sql.reserve()` to hold a dedicated postgres.js connection per request, manually `BEGIN`, `SET LOCAL app.current_user_id`, `COMMIT`/`ROLLBACK` in Fastify lifecycle hooks.

**Why:** `SET LOCAL` scopes the variable to the current transaction — context resets automatically when the transaction ends, preventing leakage across pooled connections. `sql.begin()` was rejected because its callback wrapper is incompatible with Fastify's multi-hook request lifecycle.

---

## Multiple organizations per user

**Decision:** Users can be members of multiple organizations. `organization_memberships` is a join table with a composite PK on `(user_id, organization_id)`.

**Why:** A user might want conceptual separation between multiple different ecosystems within Aleph. Multi-org is the right default.

---

## Organization membership roles: `owner`, `admin`, `member`, `viewer`

**Decision:** Four roles as a Postgres enum on `organization_memberships`.

**Why:** Covers the range from full control (`owner`) to read-only access (`viewer`). RLS only checks membership presence, not role — roles are application-layer authorization.

---

## RLS isolation boundary: org-level (not domain-level)

**Decision:** RLS policies enforce org-level isolation for now. Domain-level access control is deferred.

**Why:** Domain membership is in scope eventually but not for this phase. Org-level isolation is sufficient for MVP and simpler to implement correctly.

---

## Connections, sub-domains, SDK/CLI, email, and search are MVP scope

**Decision:** All in scope for MVP: Connections between Points, sub-domain hierarchy, SDK/CLI publish workflow, email sending for magic links, search and discovery.

**Why:** These are either core to the value proposition (Connections, search) or prerequisite infrastructure (email, SDK/CLI). None can be deferred without significantly compromising the product.

---

## Admin reporting dashboard is post-MVP

**Decision:** A special admin view with ecosystem-wide insights is explicitly deferred. All roles see the same UI for MVP.
