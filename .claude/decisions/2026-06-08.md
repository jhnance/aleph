# Decisions — 2026-06-08

## Export-scoping rule: version-level enforcement, point-level use cases always valid

**Decision:** Removed the point-level export-scoping constraint on `use_case_lineages` (which blocked null `export_id` lineages if any version of the point had ever had exports). Replaced with a version-level trigger on `point_version_use_cases`: if a lineage is export-scoped (`export_id IS NOT NULL`), the referenced export must be present in the specific version being associated. Point-level lineages (`export_id IS NULL`) are always allowed, regardless of whether the point has exports.

Also removed `UNIQUE (point_id, export_id)` from `use_case_lineages` — it inadvertently limited each export to one lineage, contradicting the definition of a use case as a single distinct behavior (an export can have many).

The trigger condition `v_export_id IS NOT NULL AND NOT EXISTS (...)` reads: "this lineage claims to belong to a specific export AND that export isn't in this version's manifest." The only blocked case is the last row below:

| scenario | `v_export_id IS NOT NULL` | `NOT EXISTS (...)` | raises? |
|---|---|---|---|
| point-level use case (`export_id = NULL`) | false | — | no (short-circuits) |
| export-scoped, export in version | true | false | no |
| export-scoped, export NOT in version | true | true | **yes** |

**Why:** The old constraint was too broad in two ways: (1) it prevented point-level use cases (e.g., "when imported, the module initializes without side effects") on points that also have exports, and (2) "any version ever" semantics would retroactively affect older versions that never had exports. The new trigger enforces referential integrity at the right granularity — the specific version being associated — without over-constraining what kinds of lineages are valid.

## No retroactive export association when exports are first declared

**Decision:** When a point publishes its first export-declaring version (having previously published versions with no exports), existing null-`export_id` lineages are not retroactively associated with the new exports. Pre-declaration history is preserved and queryable but remains unlinked from specific exports. New export-scoped lineages start from the first version that declares them.

**Why:** Retroactive association requires user disambiguation (which export does each historical use case belong to?) — non-trivial UX with no clean automated answer. More fundamentally, Aleph's data is based on declared state, not inferred code state: v1.0.0's declared state was "no exports," and that's immutable. The bounded loss (pre-declaration history unlinked from exports) is preferable to a special-case carve-out inside an otherwise immutable system.
