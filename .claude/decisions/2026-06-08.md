# Decisions — 2026-06-08

## Export-scoping rule: version-level enforcement, point-level use cases always valid

**Decision:** Version-level trigger on `point_version_use_cases`: if a lineage is export-scoped (`export_id IS NOT NULL`), the referenced export must be present in the specific version being associated. Point-level lineages (`export_id IS NULL`) are always allowed. Also removed `UNIQUE (point_id, export_id)` from `use_case_lineages` — it inadvertently limited each export to one lineage.

The trigger raises only for the last case:

| scenario | `v_export_id IS NOT NULL` | `NOT EXISTS (...)` | raises? |
|---|---|---|---|
| point-level use case (`export_id = NULL`) | false | — | no |
| export-scoped, export in version | true | false | no |
| export-scoped, export NOT in version | true | true | **yes** |

**Why:** The old constraint was too broad: it blocked point-level use cases (e.g., "module initializes without side effects") on points that also have exports, and used "any version ever" semantics that would retroactively affect older versions. The trigger enforces referential integrity at the right granularity — the specific version being associated.

---

## No retroactive export association when exports are first declared

**Decision:** When a point publishes its first export-declaring version, existing null-`export_id` lineages are not retroactively associated with the new exports. Pre-declaration history is preserved but remains unlinked from specific exports.

**Why:** Retroactive association requires user disambiguation (which export does each historical use case belong to?) with no clean automated answer. Aleph's data is based on declared state, not inferred: v1.0.0's declared state was "no exports," and that's immutable.
