# Decisions — 2026-06-12

## Invite flow: consent-gated invitations riding the magic-link machinery

**Context:** Review checklist 4.1 — promote the org-join open question (invite link vs. direct email add vs. self-join) to a designed use case.

**Decision:** Invitation-only, consent-gated. An admin+ invites `{ email, role }` (`viewer|member|admin`; `owner` not invitable); a pending `org_invitations` row grants nothing until acceptance creates the membership. Acceptance paths: the invite link (unauthenticated atomic redemption that also signs the invitee in — reusing the magic-link token shape: 32 bytes, SHA-256, single-use `UPDATE ... RETURNING`) or explicit accept from the org-selection / create-org screens, which surface pending invitations; nothing auto-converts at sign-in. Resend = revoke + fresh row; rows are never deleted (tombstones `accepted_at`/`revoked_at`); one live invitation per (org, email) via partial unique index; creation is rate-limited and anti-enumeration-uniform. RLS: three-plane policy (admin org branch, invitee email branch, capability-keyed `app.invite_code_hash` redemption branch) with access matrix in `data-model.md`. Domain auto-join deferred post-MVP (ALIGNMENT.md non-goal).

**Rationale:** In a magic-link system email ownership *is* identity, so "send invite link" and "add email directly" converge — except on consent, and consent-gating costs nothing extra while avoiding memberships nobody asked for. Reusing the auth machinery means no second token system to secure. The membership insert happens as the invitee (user-id branch of the memberships policy), resolving the 3.2 follow-up with no policy change. Direct-add and auto-join remain possible later as additive flows.

## Read-path catalog surfaces designed

**Context:** Review checklist 4.2 — the four catalog stubs (browse, point detail, view use case, ecosystem map) promoted to designed use cases.

**Decision:** Browse = domain-tree sidebar + point list (file-browser pattern; SPA deep-links domains by sibling-scoped slug *path*; one list with `status=active` default rather than separate views; keyset pagination). Point detail = one aggregate endpoint anchored on the representative version — latest `release`, falling back to latest-of-any-classification, badged; a directly visited no-version point renders an unpublished nudge (whether such points are *listed* in browse is pinned — see `browse-catalog.md`). View use case = **lineage-addressed** (the lineage UUID is the page identity); per-appearance content records keep old versions historically accurate; cross-version diff deferred. Demo playback = separate registrable domain + `sandbox="allow-scripts"` iframe without `allow-same-origin` (org-authored bundles are untrusted: same-site hosting would make every demo a stored-XSS vector against colleagues' sessions). Ecosystem map = domain-scoped only for MVP, with **boundary nodes** (`inDomain: false`) so cross-domain dependencies stay visible; one nodes+edges response; org-wide and focal-point views deferred over the same shape.

**Rationale:** The read path serves every discipline (health in particular is an interdisciplinary, ecosystem-wide concern); criteria are written from catalog-consumer tasks rather than publisher tasks. Representative-version anchoring and the point-level rollup were already decided (2026-06-10); the fallback and addressing choices follow from lineage being the only stable identity. The sandbox decision is the standard usercontent-isolation pattern and got the access-matrix treatment.

## Bulk onboarding: users' own AI tools, guided by Aleph-provided Skills docs

**Context:** Review checklist 4.3 — the AI-driven bulk-onboarding story. The fork was where the AI runs: CLI-integrated (user-brought key), Aleph-hosted, or neither.

**Decision:** Neither — Aleph does not run the AI. Aleph ships **Skills documents** that users plug into their own AI workflows (Claude Code, Cursor, etc.), directing their tools to analyze the codebase into an **onboarding manifest**; the CLI validates and applies the confirmed manifest (confirm-before-write, like `aleph scan`). Aleph-hosted inference is tabled until much later than MVP. The use case remains a deliberate stub; manifest format, apply semantics, and domain-proposal scope are designed when needed.

**Rationale:** No inference costs, no org source code transiting Aleph, no model-provider coupling — and it meets users inside AI tooling they already operate. The deterministic substrate (workspace detection, config scaffolding, bulk apply) stays in the CLI regardless of which tool produced the manifest.

## Org-staleness corpus sweep (6.5)

**Context:** The 3.4 decision (2026-06-11, URL-org-authoritative) deleted the JWT `org` claim, the `org_context_mismatch` error, and the switch-org endpoint, but the sweep never reached the ~20 individual use-case files. They still said "must match the session's active org; mismatch 403 (`org_context_mismatch`); no active org → 400" and "`organization_id` from the session JWT" — actively contradicting the security decision.

**Decision:** Replaced the stale per-file authz blurb everywhere with the canonical post-3.4 form: *"the org is resolved from `:orgSlug` by the per-request slug⋈membership query; a user with no membership in that org gets 404 (tenant-hiding); unauthenticated → 401."* `organization_id` now reads "the org resolved from `:orgSlug`," never the JWT. `create-organization.md` lost the obsolete `switchToOrg`/JWT-reissue machinery — entering a new org is pure navigation. CLI files (`aleph-sync`, `aleph-new-use-case`, `export-rename-succession`, `cli-auth`) state there is **no CLI org-switch command and no "active org" state**: a multi-org CLI user acts in whichever org `aleph.config.ts` declares.

**Rationale:** A spec that contradicts its own security model is worse than no spec — the next implementer would code the deleted 403/400 paths. One canonical sentence applied uniformly also makes future drift greppable.

## CLI device-authorization flow (6.6)

**Context:** `cli-auth.md` said the CLI "polls for the resulting JWT" after a magic link, but no endpoint provided that, and `GET /api/auth/verify` mints an `HttpOnly` cookie the CLI can't read — so the implied device-code surface had to be designed or dropped.

**Decision:** Design it, reusing the magic-link machinery (RFC 8628-shaped). `POST /api/auth/cli/start { email }` creates one `auth_codes` row carrying both `code_hash` (emailed token) and `device_code_hash` (SHA-256 of the 32-byte `deviceCode` returned to the CLI), emails a normal magic link, and returns `{ deviceCode, interval, expiresIn }` (rate-limited + anti-enumeration like `magic-link`). The user clicks the link; `GET /api/auth/verify` redeems the row unchanged — stamping `used_at` *is* the device-approval signal (no change to verify). The CLI polls `POST /api/auth/cli/token { deviceCode }`: `authorization_pending` while `used_at` is null, `slow_down` if it polls faster than `interval`, `expired_token` if gone; once approved it mints a CLI identity JWT (same `sub`/`exp`/`iat`/`jti` shape, 90-day lifetime, accepted via `Authorization: Bearer`), stamps `device_consumed_at` (single-use), and returns `{ token }`. DDL: `device_code_hash` + `device_consumed_at` columns on `auth_codes` + partial unique index.

**Rationale:** A cookie can't reach the CLI, so the CLI needs its own grant; binding the device request to the same `auth_codes` row that already powers magic-link means no second token system to secure and no change to the verify path. The device code is a 256-bit secret hashed at rest exactly like the magic token; single-use minting closes replay.

**Open (security, not resolved here):** silent approval-on-link-click opens an **account-takeover** vector (attacker starts the flow with the victim's email, phishes the click, polls out a token for the victim's account). The RFC 8628 `user_code`-confirmation step is the standard fix — binding approval to *this* device with explicit human intent. Flagged in `cli-auth.md` ("Open — device-flow approval intent") for a dedicated adversarial beat with the access-matrix treatment before the use case leaves To Do. The 6.6 walkthrough designed the *transport*; the *consent* step still needs deciding.
