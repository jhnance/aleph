# Decisions — 2026-06-12

## Invite flow: consent-gated invitations riding the magic-link machinery

**Decision:** Invitation-only, consent-gated. An admin+ invites `{ email, role }` (`viewer|member|admin`; `owner` not invitable); a pending `org_invitations` row grants nothing until acceptance. Acceptance paths: the invite link (unauthenticated atomic redemption that also signs the invitee in — reusing the magic-link token shape: 32 bytes, SHA-256, single-use `UPDATE ... RETURNING`) or explicit accept from the org-selection/create-org screens. Resend = revoke + fresh row; one live invitation per (org, email) via partial unique index; creation is rate-limited and anti-enumeration-uniform. RLS: three-plane policy (admin org branch, invitee email branch, capability-keyed `app.invite_code_hash` redemption branch) with access matrix in `data-model.md`. Domain auto-join deferred post-MVP.

**Why:** In a magic-link system email ownership *is* identity, so "send invite link" and "direct email add" converge — except on consent. Reusing the auth machinery means no second token system to secure. The membership insert happens as the invitee (user-id branch of the memberships policy), resolving the 3.2 follow-up with no policy change.

## Read-path catalog surfaces designed

**Decision:** Browse = domain-tree sidebar + point list (keyset pagination; `status=active` default; SPA deep-links domains by sibling-scoped slug path). Point detail = aggregate endpoint anchored on the representative version (latest `release`, falling back to latest-of-any-classification, badged; a no-version point renders an unpublished nudge). View use case = **lineage-addressed** (lineage UUID is page identity); per-appearance content records keep old versions historically accurate; cross-version diff deferred. Demo playback = separate registrable domain + `sandbox="allow-scripts"` iframe without `allow-same-origin` (org-authored bundles are untrusted — same-site hosting makes every demo a stored-XSS vector against colleagues' sessions). Ecosystem map = domain-scoped with **boundary nodes** (`inDomain: false`) so cross-domain dependencies stay visible; org-wide and focal-point views deferred.

**Why:** Demo sandboxing is the standard usercontent-isolation pattern and got the access-matrix treatment. Representative-version anchoring and lineage addressing follow from prior decisions (2026-06-10).

## Bulk onboarding: users' own AI tools, guided by Aleph-provided Skills docs

**Decision:** Aleph ships **Skills documents** that users plug into their own AI workflows (Claude Code, Cursor, etc.), directing those tools to analyze the codebase into an **onboarding manifest**; the CLI validates and applies the confirmed manifest (confirm-before-write, like `aleph scan`). Aleph-hosted inference is tabled until post-MVP. The use case remains a deliberate stub; manifest format, apply semantics, and domain-proposal scope are designed when needed.

**Why:** No inference costs, no org source code transiting Aleph, no model-provider coupling — and it meets users inside AI tooling they already operate.

## CLI device-authorization flow (6.6)

**Decision:** RFC 8628-shaped flow reusing the magic-link machinery. `POST /api/auth/cli/start { email }` creates one `auth_codes` row carrying both `code_hash` (emailed token) and `device_code_hash` (SHA-256 of the 32-byte `deviceCode` returned to the CLI), emails a normal magic link, and returns `{ deviceCode, interval, expiresIn }` (rate-limited + anti-enumeration). The user clicks the link; `GET /api/auth/verify` redeems the row unchanged — stamping `used_at` is the device-approval signal. The CLI polls `POST /api/auth/cli/token { deviceCode }`: `authorization_pending` while `used_at` is null, `slow_down` if polling faster than `interval`, `expired_token` if gone; once approved it mints a 90-day CLI JWT, stamps `device_consumed_at` (single-use), returns `{ token }`. DDL: `device_code_hash` + `device_consumed_at` columns on `auth_codes` + partial unique index.

**Why:** A cookie can't reach the CLI, so the CLI needs its own grant. Binding the device request to the same `auth_codes` row that powers magic-link means no second token system to secure and no change to the verify path.

**Open (security — not resolved here):** silent approval-on-link-click opens an account-takeover vector (attacker starts the flow with the victim's email, phishes the click, polls out a token). The RFC 8628 `user_code`-confirmation step is the standard fix. Flagged in `cli-auth.md` ("Open — device-flow approval intent") for a dedicated adversarial beat before the use case leaves To Do.
