# DB Migration Options

Three options compared side-by-side using Aleph's domain as the example.

---

## Option A: Raw SQL migrations + postgres.js

You write `.sql` files by hand. A small script tracks which ones have run. postgres.js handles all queries directly.

### File layout

```
apps/api/
  migrations/
    0001_create_orgs.sql
    0002_create_points.sql
  src/
    db.ts          ← postgres.js connection
    migrate.ts     ← migration runner script
```

### Migration files

```sql
-- migrations/0001_create_orgs.sql
CREATE TABLE orgs (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT        NOT NULL,
  slug        TEXT        NOT NULL UNIQUE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

```sql
-- migrations/0002_create_points.sql
CREATE TABLE points (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT        NOT NULL,
  org_id      UUID        NOT NULL REFERENCES orgs(id),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### Migration runner

```ts
// src/migrate.ts
import postgres from 'postgres'
import fs from 'fs'
import path from 'path'

const sql = postgres(process.env.DATABASE_URL!)

// Tracking table — created once, idempotent
await sql`
  CREATE TABLE IF NOT EXISTS _migrations (
    filename    TEXT        PRIMARY KEY,
    applied_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
  )
`

const applied = new Set(
  (await sql`SELECT filename FROM _migrations`).map(r => r.filename)
)

const files = fs.readdirSync('./migrations')
  .filter(f => f.endsWith('.sql'))
  .sort()

for (const file of files) {
  if (applied.has(file)) continue

  const content = fs.readFileSync(path.join('./migrations', file), 'utf8')

  await sql.begin(async sql => {
    await sql.unsafe(content)
    await sql`INSERT INTO _migrations (filename) VALUES (${file})`
  })

  console.log(`Applied: ${file}`)
}

await sql.end()
```

Run it: `npx tsx src/migrate.ts`

### Queries (postgres.js)

```ts
// src/db.ts
import postgres from 'postgres'
export const sql = postgres(process.env.DATABASE_URL!)
```

```ts
import { sql } from './db'

// Select
const points = await sql`
  SELECT p.id, p.name, o.slug AS org_slug
  FROM points p
  JOIN orgs o ON o.id = p.org_id
  WHERE p.org_id = ${orgId}
  ORDER BY p.created_at DESC
`

// Insert
const [point] = await sql`
  INSERT INTO points (name, org_id)
  VALUES (${name}, ${orgId})
  RETURNING *
`
```

**Tradeoffs:**
- You write real SQL — nothing is hidden from you
- No type safety on query results (you get `any[]`)
- Migration files are readable diffs — easy to understand in code review
- The runner above is ~20 lines; you own it entirely

## Option B: postgres.js for queries + Drizzle Kit for migrations only

You define a Drizzle schema in TypeScript — Drizzle Kit uses it to generate SQL migration files. But you still write all app queries in postgres.js directly, not through Drizzle's query API.

The Drizzle schema exists only as the source of truth for your table shape; it generates migrations, but the query layer ignores it.

### File layout

```
apps/api/
  migrations/
    0000_create_orgs.sql    ← generated by drizzle-kit
    0001_create_points.sql  ← generated by drizzle-kit
  src/
    schema.ts      ← drizzle table definitions (for migration generation)
    db.ts          ← plain postgres.js connection
  drizzle.config.ts
```

### Schema (TypeScript)

```ts
// src/schema.ts
import { pgTable, uuid, text, timestamp } from 'drizzle-orm/pg-core'

export const orgs = pgTable('orgs', {
  id:        uuid('id').primaryKey().defaultRandom(),
  name:      text('name').notNull(),
  slug:      text('slug').notNull().unique(),
  createdAt: timestamp('created_at').notNull().defaultNow(),
})

export const points = pgTable('points', {
  id:        uuid('id').primaryKey().defaultRandom(),
  name:      text('name').notNull(),
  orgId:     uuid('org_id').notNull().references(() => orgs.id),
  createdAt: timestamp('created_at').notNull().defaultNow(),
})
```

### Drizzle Kit config

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema:  './src/schema.ts',
  out:     './migrations',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URL!,
  },
})
```

### Migration workflow

```bash
# After changing schema.ts, generate a new migration file:
npx drizzle-kit generate

# Apply pending migrations to the DB:
npx drizzle-kit migrate
```

`generate` diffs your schema against the last snapshot and writes a `.sql` file to `./migrations/`. `migrate` runs any unapplied ones.

### Queries (still plain postgres.js)

```ts
// src/db.ts
import postgres from 'postgres'
export const sql = postgres(process.env.DATABASE_URL!)
```

```ts
import { sql } from './db'

// Exactly the same as Option A — Drizzle is not involved here
const points = await sql`
  SELECT p.id, p.name
  FROM points p
  WHERE p.org_id = ${orgId}
`
```

**Tradeoffs:**
- Migration generation is automated — you change a TypeScript file, not SQL
- You still write raw SQL for queries, so no type safety on results
- The schema.ts exists but is only used by the CLI, which feels slightly redundant
- Migrations are still readable `.sql` files

## Option C: Drizzle for everything

Same schema as Option B, but you use Drizzle's query API for all app queries too. postgres.js becomes the underlying transport; Drizzle sits on top.

### File layout

```
apps/api/
  migrations/          ← same as Option B, generated by drizzle-kit
  src/
    schema.ts          ← same as Option B
    db.ts              ← drizzle instance wrapping postgres.js
  drizzle.config.ts    ← same as Option B
```

### DB connection

```ts
// src/db.ts
import postgres from 'postgres'
import { drizzle } from 'drizzle-orm/postgres-js'
import * as schema from './schema'

const client = postgres(process.env.DATABASE_URL!)
export const db = drizzle(client, { schema })
```

### Queries (Drizzle query API)

```ts
import { db } from './db'
import { points, orgs } from './schema'
import { eq } from 'drizzle-orm'

// Select with join — fully type-safe
const rows = await db
  .select({ id: points.id, name: points.name, orgName: orgs.name })
  .from(points)
  .innerJoin(orgs, eq(points.orgId, orgs.id))
  .where(eq(points.orgId, orgId))
// rows: { id: string, name: string, orgName: string }[]

// Insert
const [point] = await db
  .insert(points)
  .values({ name, orgId })
  .returning()
// point: { id: string, name: string, orgId: string, createdAt: Date }

// When you need SQL that Drizzle's API doesn't express cleanly:
import { sql } from 'drizzle-orm'

const result = await db.execute(sql`
  WITH RECURSIVE descendants AS (
    SELECT id, predecessor_version_id FROM point_versions WHERE id = ${versionId}
    UNION ALL
    SELECT v.id, v.predecessor_version_id
    FROM point_versions v
    JOIN descendants d ON v.predecessor_version_id = d.id
  )
  SELECT id FROM descendants
`)
```

### Migration workflow

Identical to Option B — `drizzle-kit generate` + `drizzle-kit migrate`.

**Tradeoffs:**
- Full type safety end-to-end: TypeScript knows the shape of every query result
- The schema is the single source of truth for both migrations and queries
- Drizzle's query API covers ~90% of cases; the `sql` escape hatch handles the rest (and you'll use it — your publish-use-case recursive CTE is a good example)
- Slightly more to learn upfront, but the TS feedback loop speeds you up once you're past it

## Option D: Kysely

Kysely is a type-safe SQL query builder — closer to raw SQL than Drizzle's API, but with full TypeScript inference. The key difference from Drizzle: your "schema" is just TypeScript interfaces (no runtime objects), and migrations are TypeScript files you write yourself — there's no code generation step.

### File layout

```
apps/api/
  migrations/
    0001_create_orgs.ts    ← you write these (TS, not SQL)
    0002_create_points.ts
  src/
    schema.ts      ← TypeScript interfaces only (no runtime objects)
    db.ts          ← kysely instance
    migrate.ts     ← migration runner
```

### Schema (TypeScript interfaces)

```ts
// src/schema.ts
import { Generated } from 'kysely'

interface OrgsTable {
  id:         Generated<string>
  name:       string
  slug:       string
  created_at: Generated<Date>
}

interface PointsTable {
  id:         Generated<string>
  name:       string
  org_id:     string
  created_at: Generated<Date>
}

export interface Database {
  orgs:   OrgsTable
  points: PointsTable
}
```

`Generated<T>` marks columns the DB fills in (`DEFAULT`) — Kysely omits them from insert types automatically.

### DB connection

```ts
// src/db.ts
import postgres from 'postgres'
import { Kysely } from 'kysely'
import { PostgresJSDialect } from 'kysely-postgres-js'
import { Database } from './schema'

const client = postgres(process.env.DATABASE_URL!)

export const db = new Kysely<Database>({
  dialect: new PostgresJSDialect({ postgres: client }),
})
```

### Migration files

Kysely migrations are TypeScript files with `up` and `down` exports. You can use Kysely's schema builder API or drop to raw SQL:

```ts
// migrations/0001_create_orgs.ts
import { Kysely, sql } from 'kysely'

export async function up(db: Kysely<any>): Promise<void> {
  await db.schema
    .createTable('orgs')
    .addColumn('id',         'uuid',        col => col.primaryKey().defaultTo(sql`gen_random_uuid()`))
    .addColumn('name',       'text',        col => col.notNull())
    .addColumn('slug',       'text',        col => col.notNull().unique())
    .addColumn('created_at', 'timestamptz', col => col.notNull().defaultTo(sql`NOW()`))
    .execute()
}

export async function down(db: Kysely<any>): Promise<void> {
  await db.schema.dropTable('orgs').execute()
}
```

Or if the schema builder API gets unwieldy (complex constraints, CTEs in migrations), drop straight to SQL:

```ts
export async function up(db: Kysely<any>): Promise<void> {
  await sql`
    CREATE TABLE orgs (
      id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
      name        TEXT        NOT NULL,
      slug        TEXT        NOT NULL UNIQUE,
      created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
    )
  `.execute(db)
}
```

### Migration runner

Kysely ships a `Migrator` class — you point it at your migration files and it tracks what's been applied:

```ts
// src/migrate.ts
import { Migrator, FileMigrationProvider } from 'kysely'
import { db } from './db'
import path from 'path'
import { promises as fs } from 'fs'

const migrator = new Migrator({
  db,
  provider: new FileMigrationProvider({
    fs,
    path,
    migrationFolder: path.join(import.meta.dirname, '../migrations'),
  }),
})

const { error, results } = await migrator.migrateToLatest()

results?.forEach(r => {
  if (r.status === 'Success') console.log(`Applied: ${r.migrationName}`)
  if (r.status === 'Error')   console.error(`Failed:  ${r.migrationName}`)
})

if (error) process.exit(1)
await db.destroy()
```

Run it: `npx tsx src/migrate.ts`

### Queries

```ts
import { db } from './db'

// Select with join — fully type-safe, reads like SQL
const rows = await db
  .selectFrom('points')
  .innerJoin('orgs', 'orgs.id', 'points.org_id')
  .select(['points.id', 'points.name', 'orgs.name as org_name'])
  .where('points.org_id', '=', orgId)
  .execute()
// rows: { id: string, name: string, org_name: string }[]

// Insert
const point = await db
  .insertInto('points')
  .values({ name, org_id: orgId })
  .returningAll()
  .executeTakeFirstOrThrow()
// point: { id: string, name: string, org_id: string, created_at: Date }

// Raw SQL escape hatch (same as Drizzle)
import { sql } from 'kysely'

const result = await sql`
  WITH RECURSIVE descendants AS (
    SELECT id, predecessor_version_id FROM point_versions WHERE id = ${versionId}
    UNION ALL
    SELECT v.id, v.predecessor_version_id
    FROM point_versions v
    JOIN descendants d ON v.predecessor_version_id = d.id
  )
  SELECT id FROM descendants
`.execute(db)
```

**Tradeoffs:**
- Full type safety like Drizzle, but the query API reads more like SQL (`.selectFrom`, string column names) vs. Drizzle's object references
- No code generation — migrations are files you write, not diffs computed from a schema snapshot
- `down` migrations give you a rollback path (Drizzle doesn't generate these)
- TypeScript interfaces are lighter than Drizzle's runtime table objects — nothing to import in query files beyond `db`
- Slightly less magic overall; what you write is closer to what executes

## Side-by-side summary

|                          | Raw SQL        | postgres.js + Drizzle Kit  | Drizzle everything         | Kysely                        |
|--------------------------|----------------|----------------------------|----------------------------|-------------------------------|
| Migration authoring      | Write SQL      | Edit TypeScript schema     | Edit TypeScript schema     | Write TypeScript files        |
| Migration files          | You write them | Auto-generated SQL         | Auto-generated SQL         | You write them (TS)           |
| Rollback (`down`)        | Manual         | No                         | No                         | Yes (built-in)                |
| Query type safety        | None           | None                       | Full                       | Full                          |
| Query syntax             | SQL strings    | SQL strings                | TypeScript API + SQL hatch | SQL-like TS API + SQL hatch   |
| Schema definition        | None           | Runtime table objects      | Runtime table objects      | Plain TS interfaces           |
| postgres.js still used   | Yes            | Yes (queries)              | As transport only          | As transport only             |
| Learning curve           | Low            | Low                        | Medium                     | Medium                        |
